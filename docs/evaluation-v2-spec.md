# 再生観測に基づく評価 v2：仕様案

- 作成日：2026-10-14。対象は依頼された①評価仕様、②GroundTruth生成、③Evaluator・Runnerの拡張。
- 状態：2026-10-14にユーザー確認済み。既存の二値・未聴曲評価をv1、新しい評価を`listening-v2`として区別する。
- 実装状況：本仕様のEvaluator・GroundTruth拡張は未着手。今回の[検証・探索フロー](experiment-workflow.md)は既存Binary評価で実装し、Gradedは未測定として区別する。検証フローのK感度は最新依頼に従い1〜20とする。
- 根拠：[Train／Validationの分析](../experiments/music4all/ground-truth.md)、[一次資料の整理](../experiments/music4all/ground-truth-methods.md)。DBのテーブル統合はこの依頼に含めない。

## 目的と完了条件

元の保存済み分割から回数・再生日数を保持したGroundTruthを生成し、新規発見・既聴曲の再聴・新規曲の定着を別々に評価する。新規曲と既聴曲の推薦をそれぞれ一度だけ生成し、同じランキングを期間・K・gainの設定を変えて評価する。

- 新旧形式を区別して読み込み、既存の合成データ・保存済み入力・二値評価が引き続き使える。
- GroundTruthを作る際、未来の再生によって学習履歴・ユーザー選定・候補集合が変わらない。
- 新規発見と新規曲の定着で推薦を重複生成しない。K・評価期間・日数の重みを変えても推薦関数を呼び直さない。
- IDCGの分母、正解なしユーザー、推薦失敗・不正出力、短いランキングを一意に処理する。
- 合成イベントと手計算で検証し、CLIから新しい入力・結果を保存できる。今回、新条件で実データのモデル性能を測る作業は含めない。

## 評価条件

| 項目 | v2の仕様案 |
| --- | --- |
| 主評価期間 | 推薦時点から90日 |
| 期間感度 | 同じ推薦時点から30日・180日。各窓は開始以上・終了未満 |
| Validationの推薦時点 | 元のTrain終端、既定2017-03-29 00:00:00 |
| Validationの学習 | 元のTrain全期間。90日窓の終了は2017-06-27 00:00:00 |
| Testの推薦時点 | 元のValidation終端、既定2018-09-21 00:00:00 |
| Testの学習 | 元のTrain＋Validation全期間。評価窓に合わせて学習範囲を切り直さない |
| ユーザー | 学習履歴のあるユーザー。未来の活動・正解の有無では選ばない |
| カタログ | 学習期間に観測された曲。評価期間に初登場するcold itemは候補に追加しない |
| 日数 | 配布時刻の日付の異なり数。timezone-naiveを保持し、UTC・JSTを割り当てない |
| K | 主評価10、補助5・20、感度2〜20。推薦要求は上位20曲 |
| 関連度 | 下記gainをEvaluatorで計算。GroundTruthには計算済みスコアを保存しない |

Validationの評価窓が元のTest開始を越える設定は拒否する。Testの各評価窓の終了日時は結果に記録する。ログの最終再生時刻を、各ユーザーがその窓の末尾まで観測された保証としては使わない。

### 候補と評価の対応

`C`を学習カタログ、`H(u)`を本人の学習期間のユニーク既聴曲とする。

| 保存するランキング | 候補 | 算出する指標 |
| --- | --- | --- |
| `new` | `C − H(u)` | 新規発見のBinary NDCG・Recall、新規曲の定着のGraded NDCG |
| `repeat` | `C ∩ H(u)` | 既聴曲の再聴のGraded NDCG・Repeat Recall |

- 候補集合を推薦要求に持たせ、モデルとEvaluatorが同じルールを使う。既存要求は既定で`new`とし、v1の既聴除外動作を維持する。
- 候補が空の要求も記録し、推薦関数は呼ばず空の結果を保存する。正解なしとして精度平均から除外し、空候補件数を示す。
- 新規は学習履歴上の未聴であり、生涯で初めて聴いた保証ではない。新規Graded NDCGは定着の代理指標であり、推薦の因果効果ではない。

## GroundTruthの保存と生成

### 生成物

v2は新規ディレクトリに次のファイルを保存する。保存済みsnapshot / splitを変更せず、DB migrationや新テーブルを追加しない。

| ファイル | 内容 |
| --- | --- |
| `manifest.json` | `schema_version=2`、`protocol=listening-v2`、出典、境界、窓、形式・行数・SHA-256、生成処理版 |
| `learning.parquet` | 学習期間のユーザー×曲別の再生回数・再生日数。全学習ユーザー・カタログ・履歴をここから決める |
| `observations.parquet` | 窓別の評価期間の観測事実。下記の列を保持する |

`learning.parquet`の列：`user_id`, `item_id`, `play_count`, `active_days`。

`observations.parquet`の列：

| 列 | 意味 |
| --- | --- |
| `user_id`, `item_id` | データセットの元ID。先頭ゼロ・大文字小文字を維持 |
| `window_days` | 評価窓の日数 |
| `learning_play_count`, `learning_active_days` | 同じ組の学習期間の回数・日数。未聴ならともに0 |
| `evaluation_play_count`, `evaluation_active_days` | その評価窓内の回数・日数 |

- 観測行はその窓で評価再生があるwarm user / warm itemの組だけを保存する。同じ候補に行がなければ、その窓で再生を観測していないものとしてgainを0にする。嫌いという意味にはしない。
- ユーザー全員と候補の全直積は保存しない。正解なしユーザーも`learning.parquet`から復元できる。
- `learning_play_count=0`なら`new`、正なら`repeat`。重複する分類ラベルや、計算済み関連度を観測列へ追加しない。
- `(user_id,item_id)`または`(user_id,item_id,window_days)`を対応するファイル内の一意なキーとする。
- 回数・日数は整数、`0 <= active_days <= play_count`、回数0と日数0は同時。観測行の評価回数・日数はともに1以上。
- 同日内の複数イベントは回数に加算し、日数は1日。元イベントの重複も勝手に削除しない。
- cold user / cold itemはこの順で排他的に分類し、窓別の除外件数をmanifestへ記録する。再聴は除外ではなく別タスクとなる。

### 取り込み境界と検証

- 元分割の形式・SHA-256・境界・snapshot / splitの出典を照合した上で生成する。学習集計と評価集計を別々に行う。
- Validationの生成にTestイベントを使わない。Testの生成も学習にはTrain＋Validationだけを使う。
- 全量生成はユーザーhashによる分割とディスク上の中間保存を使い、DuckDBの2GB・2スレッドを既定にする。全量をPythonの辞書や集合へ読み込まない。2GBはプロセス全体の上限ではない。
- 集計した回数の合計・日数の範囲・一意性・warm条件を確認し、書出し後にファイルを読み戻して照合する。manifestは全検証後に保存する。不完全な出力にmanifestを付けない。
- 出力ディレクトリは新規に限り、既存結果を上書きしない。生成物は`data/`配下、集計・共有用文書は`experiments/`配下とする。
- manifest内の保存物参照はbundle内の相対パスとし、絶対パスや親ディレクトリへの移動を拒否する。出典には元保存物のhashとstorage keyを保持する。
- 出力の行順・JSON・Parquet writer設定を固定し、同じ入力・設定で同じ内容hashを得る。実行日時を内容hashへ含めない。

## Evaluator

### 指標

`n`を評価窓の再生回数、`d`を異なる再生日数とする。

```text
binary_gain(n) = 1 if n >= 1 else 0
graded_gain(n,d,λ) = log2(1+n) + λ × log2(1+d)
DCG@K = Σ gain(item_at_rank_r) / log2(r+1), r=1..K
NDCG@K = DCG@K / IDCG@K
Recall@K = 先頭K位置で当たったユニーク正解曲数 / 候補内の全正解曲数
```

- λ=1を主条件。λ=0・0.5・2も同じ保存ランキングから計算できる設定にする。λは有限の非負数に限る。
- gainへさらに指数変換を重ねない。関連度を0・1・2・3へ離散化しない。
- IDCGはそのユーザー・タスク・窓の候補にある全正解のgainを降順に並べた上位Kから計算する。推薦された20曲だけを分母にしない。
- Repeat Recallの正解は「学習で既聴、かつ評価窓で1回以上再生」。2日・5日などの閾値を正解条件へ加えない。
- 分母が0の指標は`null`で、0点と区別する。集計は同じタスク・窓・K・λの正解保有ユーザーを等重みで平均し、全要求数・評価人数・除外人数も保存する。
- 各ユーザー・タスクは1要求とし、3観点や異なる窓を一つの平均へ混ぜない。

### 不正出力と短いランキング

- v2は返却された最初の20位置を固定し、その先頭K位置で評価する。候補外ID・重複IDはその位置でgain 0とし、後ろの曲を繰り上げない。重複曲の加点は最初の有効な出現だけ。
- 20位を超える出力は得点に使わない。超過数・候補外数・重複数・不足数を記録する。
- 有効な短いランキングの不足位置は0。推薦失敗も正解があれば0点として平均に含める。正解なしなら失敗でも`null`とし、失敗自体は件数へ残す。
- 不正なResponse型、要求ID不一致、推薦関数の例外は失敗にする。例外型だけを記録し、例外本文・秘密情報を保存しない。
- v1の既存の正規化・得点処理はそのまま残す。v2の位置保持ルールはプロトコル名とともに記録する。

## Runner・保存・CLI

- v2のLoaderはmanifest・全参照ファイルのSHA-256・列型・一意性・カタログ／履歴／観測の整合性を検証する。
- 推薦入力には学習情報・候補・タスク・要求ID・上位20件の指定だけを渡す。評価回数・評価日数・評価窓のGroundTruthを推薦モデルへ渡さない。
- 同じユーザーの`new`・`repeat`を各1回実行する。新規発見と新規定着、30・90・180日、K=2〜20、λの変更は得点計算だけで処理する。
- Runnerの小規模実行上限は既存と同じ学習ユーザー2,000人・学習イベント500万件。全量GroundTruthの生成と、全量モデル評価を混同しない。Loaderは大きさを確認してからPythonオブジェクト化する。
- 学習集計から、上限内では従来のInteraction列を回数分復元して既存の推薦モデルへ渡せるようにする。モデルの学習回数は1回、評価条件ごとに再学習しない。
- v2結果は新規実行ディレクトリへ、メタデータ・要求別ランキング・条件別指標を持つ`results.json`、集計表の`metrics.csv`、主条件の`summary.md`を保存する。
- 指標行のキーは`task`（discovery / repeat / retention_proxy）、`window_days`、`k`、`day_weight`、`metric`。二値指標の`day_weight`は`null`にして、λごとに二値指標を重複保存しない。
- レイテンシは生成要求に一度だけ記録し、窓・K・λごとに再計測・加算しない。3観点の指標を合算して総call数を増やさない。
- 条件にはprotocol、schema版、元出典・各内容hash、学習・推薦時点、窓、候補ルール、gain、K、集計・失敗・位置保持ルール、モデル設定、seed、依存lock hash、処理ソースhashを保存する。
- v2でも既存のTrackingConfigを使い、MLflow有効時は条件・集計・成果物参照だけを記録する。要求・履歴などの生データをMLflowへ送らない。
- 既存CLI・設定の既定動作はv1のまま。分割exportにv2指定を追加し、Benchmarkの設定からv2を明示選択する。設定を省略して既存入力をv2として扱わない。
- v1用の結果読込みはv2結果を明示的に拒否し、形式を取り違えた集計を防ぐ。03 Notebookのv2表示改修や感度グラフのUIはこの実装の範囲に含めず、CSVを後続分析へ渡せる状態を作る。

| まとまり | 責務 |

| 共通要求・候補の判定 | v1の既定を維持しつつ、new / repeatをモデルとEvaluatorでそろえる |
| v2データ形式・Loader | 観測値と学習情報、出典・内容hashを検証する |
| v2GroundTruth生成 | 保存済み分割から回数・日数を集計し、全量対応のbundleを生成する |
| v2Evaluator | gain、NDCG・Recall、位置保持、条件別の集計を計算する |
| v2Runner・CLI・Tracking | 推薦を一度だけ実行し、条件別の得点・生ランキング・生成時間を保存する |

これらの内部構成とファイル単位の作業順は、この仕様のレビュー後に実装計画へ落とす。新しい保存形式を既存型に無理に詰め込まず、指標計算・候補判定の共通処理は再利用する。

## 必要な検証

1. 手計算できる複数ユーザー・曲のイベントで、境界直前／一致／直後、同日内の複数再生、別日の再生、元ID表記を確認する。
2. 同じ曲の新規／既聴が学習履歴だけで決まり、cold user / cold itemが混ざらないことを確認する。未来イベントを追加・変更しても学習・候補・推薦要求が変わらない。
3. TestでTrain＋Validationを学習に使うこと、Validationの集計がTestへ越えないことを確認する。
4. 回数・日数・hash・相対パス・型・一意性の不整合、0・負値・bool・NaN・無限大の設定を拒否する。
5. binaryとgradedのNDCGを手計算と照合する。返却外に最高gainの正解がある場合、IDCGへ含まれることを確認する。
6. 同じユーザーの推薦関数はnew / repeatの各1回。K・窓・λを増やしても呼出数が増えず、newランキングが2観点で共有されることを確認する。
7. 無効ID・重複・20位超過・短い出力・失敗・空候補・正解なしを確認し、不正な位置を詰めないことを確認する。
8. CLIの生成→読込み→保存、MLflowの集計記録、v1入力・推薦・既存テストとの互換性を確認する。
9. 制限したメモリでの複数分割集計と、書出し・読戻しの件数一致を確認する。全量のPythonオブジェクト化や上限の黙示的な突破を防ぐ。
