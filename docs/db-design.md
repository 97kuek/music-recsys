# DB・データセット取り込みの合意事項

## 保存先

| 保存先 | 管理するもの |
| --- | --- |
| PostgreSQL + pgvector | 楽曲・ユーザー情報、Embedding、会話履歴、検索用データ、実験メタデータ |
| Parquet | 元データセット全量、大量の再生イベント、学習・検証・テスト用データ |

- 全データを両方に重複保存しない。推薦・検索に必要なデータはPostgreSQLへ取り込める構成にする。
- 将来のLLM / Agentへの拡張と実験の再現性を重視する。

## 識別と版

- Music4AllとTalkPlayDataは独立したベンチマークとし、初回取り込みで楽曲を統合しない。
- DB内部の一意なIDと、データセット固有の元IDを分離する。
- 内部IDはUUID、元IDはTEXTで保持する。
- 楽曲・ユーザーの元IDはデータセットごとに独立して管理する。
- 楽曲・録音の対応付けは、必要になった段階で追加できる構成にする。
- 異なるデータセットの評価データが意図せず混在しないようにする。

| 概念 | 意味 |
| --- | --- |
| データセット版 | 配布された元データの版。出典・元ファイル・チェックサムを記録 |
| メタデータスナップショット | 利用する楽曲・ユーザーと、それぞれのメタデータを固定した集合 |
| 取り込み実行履歴 | Adapterによる取り込みの実行・再実行・失敗の記録 |
| 分割 | Train / Validation / Testの条件とデータ |
| 実験実行履歴 | 実験で使用したデータ・設定と実行結果 |

## メタデータとスナップショット

- 楽曲・ユーザーの識別と、変更されるメタデータを分離する。
- 過去のメタデータを上書きせず、参照可能な状態にする。
- スナップショットは集合単位で管理し、作成後は変更できない設計にする。
- 各スナップショットが参照する楽曲・ユーザーとメタデータを固定する。
- 変更されていないメタデータ本体は再利用し、不要な重複保存を避ける。
- 初期段階では複雑なレコード単位の版管理を導入しない。
- Embeddingには生成モデル・モデル版・入力データの版を紐付ける。
- 実験にはデータセット版・スナップショット・分割・前処理・モデル設定を紐付ける。

## 初回取り込み

- Music4All-Onionから始め、小規模なサブセットで取り込み処理を検証する。
- 公開ファイルにある楽曲ID・タグと重み、ユーザーIDを対象とする。
- 曲名・アーティスト名・ユーザー属性は、未取得のため初回に含めない。[実配布ファイルの確認](music4all-import-sources.md)
- その後、再生履歴、音響特徴・Embeddingへ段階的に拡張する。
- 共通の取り込み処理と、データセット固有のAdapterを分離する。
- 元ファイルの版・チェックサム・出典を記録する。
- 共通形式への変換後に、IDの一意性・必須項目・参照整合性を検証する。
- 同じデータの再取り込みで重複しない冪等性を確保する。
- PostgreSQLとParquetへの保存・検証が完了するまでスナップショットを公開しない。
- 失敗した取り込みの途中成果を実験から参照できないようにする。
- スナップショットから、取り込み処理と元データの版を追跡できるようにする。

## DB環境

- このリポジトリ用のローカルDocker環境を用意する。
- Docker ComposeでPostgreSQL + pgvectorを構築し、両方の版を固定する。
- DBデータはDocker Volumeで永続化する。
- 接続情報は環境変数で管理し、認証情報をGitに含めない。
- スキーマ変更はAlembicで管理する。
- 将来、研究室サーバーなどへ移行できる構成にする。[設定・実行手順](local-db.md)

- テーブル・カラム・制約は[初回テーブル定義](db-schema.md)を参照。

## 初回サブセット

- 初回の件数・抽出条件は、元ID文字列順の楽曲100件・ユーザー100件に決定。[取り込み手順](music4all-import.md)
