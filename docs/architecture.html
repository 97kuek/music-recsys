現行部品を再利用

推薦器・共通Request/Response・候補検証・モデルload・Playback Adapterを土台にします。Hybridの重み付きRRFは小規模共通Runnerに実装済みで、全件・配信への統合は将来です。

同じ候補で比較する

曲の許諾・音源可否で限定した候補は、すべての比較条件で共通にします。モデルごとの上位曲から配信集合を自動選択せず、全カタログのオフライン値と縮小候補の値を区別します。

feedbackと正解を分ける

初期選択・impression・play・like・skip・満足度は役割が異なります。初期選択を実再生に数えず、like/skipをValidation正解にしません。固定条件の比較中にオンライン再学習は行いません。

補足 / 現在のコード構成と責務

推薦・実験・参加者評価のルールを、外部技術と画面表示から分ける

現在の実装

Backendはドメイン・ユースケース・内側のportと具体adapterを分離し、Frontendは表示・操作・HTTP通信を分離しています。以下はコードの責務の説明です。全体配置と処理フローは01〜04を参照してください。

Backend · Python

src/をパッケージルートとして、責務別に配置

Domain · 推薦・評価・参加者の規則src/domain/{recommendation,evaluation,study}/
src/domain/{catalog.py,datasets.py}

要求・候補・ModelSpec、評価定義、同意・セッションの契約を保持。標準ライブラリだけを使い、FastAPI・SQLite・モデル読込みへ依存しません。

Application · ユースケースと内側の契約src/application/recommendation.py
src/application/study/{runtime,sessions,recommendations,playback,catalog,snapshots,participants}.py
src/application/ports/

推薦取得、参加者の開始・再開・プロフィール・条件遷移・終了・再生bindingを担当。Domainと内側のportに依存します。Runtimeはサービスの組立のみ。セッション・推薦・再生・カタログ・保存形式を分離し、保存・音源portと共通clockを注入します。

Infrastructure · 具体adaptersrc/infrastructure/{recommenders,models,datasets,
ingestion,persistence,media,auth,config,
evaluation,research}/

推薦アルゴリズム、重みやデータの読込み、SQLite、音源、認証、実験保存など、外部技術とI/Oの詳細を担当します。

Interfaces / Bootstrap · 入力と組立src/interfaces/{http,cli,notebook}/
src/bootstrap.py

HTTP・CLI・Notebookの入口で要求を変換。Bootstrapがモデル・カタログ・音源を検証してloadし、具体adapterをRuntimeへ注入します。
